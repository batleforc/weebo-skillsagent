# Cocogitto: bump, tag, changelog

The commit-msg/pre-commit hooks and `cog install-hook` belong to `weebo-taskfile-mise`. This file
covers the release keys of the same `cog.toml` (template: `templates/cog.toml`).

## 1. What `cog bump` does

```
cog bump --auto            # semver from the conventional commits since the last tag
cog bump --minor           # or --major / --patch
cog bump --version 1.2.0   # explicit
cog bump --auto --dry-run  # prints the next version, changes nothing (safe for an agent)
```

In order:

1. Runs `pre_bump_hooks` with `{{version}}` = the bare version (`1.2.0`).
2. Writes the changelog section, unless `disable_changelog = true`.
3. Commits everything the hooks changed as `chore(version): v1.2.0`. cog commits through
   libgit2: the pre-commit and commit-msg hooks do **not** run, the commit is GPG-signed when
   the user's git config has `commit.gpgsign = true`, and it carries no `Signed-off-by` trailer.
4. Creates the tag `v1.2.0` (`tag_prefix = "v"`). It is a **lightweight** tag.
5. Runs `post_bump_hooks`.

The tag is what releases: both reference repos trigger the release workflow on a `v*` tag push.
Nothing happens on GitHub until the tag is pushed.

## 2. Pushing the tag

`git push --follow-tags` pushes annotated tags only, so it silently skips cog's tag. Either:

- push both by hand: `git push --atomic origin HEAD v1.2.0` (batlehub: no post-bump hook), or
- put that line in `post_bump_hooks` (weebo-skillsagent), so `cog bump` pushes right away.

`--atomic`: the commit and the tag land together or not at all, so the tag never points at a
commit the remote lacks.

## 3. Changelog: two modes

| Mode | Repo | Setting | When |
| --- | --- | --- | --- |
| Hand-written, Keep a Changelog | batlehub | `disable_changelog = true` | history has non-conventional commits, or the changelog is read by users and needs a narrative |
| Generated from commits | weebo-skillsagent | `disable_changelog = false` + `[changelog]` with `template = "remote"`, `remote`, `owner`, `repository` | every commit is conventional and the subjects read well on their own |

Hand-written rules (batlehub `CHANGELOG.md`):

- One `## [Unreleased]` section at the top with `### Added` / `### Changed` / `### Fixed` /
  `### Security`. Update it **in the same change** as the work, not at release time.
- At the cut, rename `[Unreleased]` to `[1.2.0] - YYYY-MM-DD`, open a new empty `[Unreleased]`,
  and update the compare links at the foot of the file:
  `[Unreleased]: …/compare/v1.2.0...HEAD` and `[1.2.0]: …/compare/v1.1.0...v1.2.0`.
  That edit goes in a commit before `cog bump`, or is staged by a pre-bump hook.

Generated mode needs nothing by hand; `cog changelog` previews it.

## 4. The pre-bump hook: one version everywhere

`task version:set VERSION={{version}}` (template `templates/.tasks/release.yaml`) writes the
version into every file that declares it, then runs `version:check`. Hook changes are staged into
the bump commit, so the tag can never point at a tree with the old version.

| File | Field | Note |
| --- | --- | --- |
| `Cargo.toml` | `[workspace.package] version` | crates use `version.workspace = true`; sed is scoped to that table |
| `Cargo.lock` | the workspace crates | `cargo metadata --offline`, never `cargo update` against the network |
| `ui/package.json` (and `docs/package.json` if any) | first `"version":` | |
| `ui/openapi.json` | `info.version` | utoipa takes it from the crate version; sed inline so no server has to run (see `weebo-api-contract`) |
| `helm/<chart>/Chart.yaml` | `version` and `appVersion` | appVersion is the image tag the chart deploys (see `weebo-helm`) |
| `helm/<chart>/README.md` | the badges | regenerated by `helm-docs` |

A repo with one crate and no UI keeps the simpler weebo-skillsagent form:

```toml
pre_bump_hooks = [
    "sed -i 's/^version = \".*\"/version = \"{{version}}\"/' crates/my-crate/Cargo.toml",
    "cargo update -p my-crate --offline",
]
```

`version:check` is also worth running in CI or `task lint`: it catches a hand edit to one file.

## 5. Traps

- `{{version}}` has no `v`. A `v` reaching Cargo.toml gives `vv1.2.0` or an unparseable chart;
  `version:set` refuses anything that is not bare semver.
- `cog bump` refuses to run on a dirty tree (untracked files included). With the changelog
  enabled it also refuses commits it cannot parse; `cog check --from-latest-tag` lists them.
- Because the git hooks do not run on the bump commit, `task lint` never sees the hook's edits:
  `version:check` inside `version:set` is the only gate there.
- A failure after the hooks (e.g. GPG signing fails) leaves their edits staged with no commit and
  no tag: `git restore --staged --worktree .` and re-run.
- A failing pre-bump hook aborts with no commit and no tag, and cog stashes what the hooks had
  changed (`git stash list` shows `cog_bump_…`). Drop or apply that stash, fix, re-run.
- Every tool a hook calls must be on the user's PATH (`helm-docs`, `node`, `cargo`): pin them in
  `mise.toml`, or the bump fails on a fresh clone.
