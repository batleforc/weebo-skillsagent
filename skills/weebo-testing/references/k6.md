# Load testing (k6)

**Trigger:** the project serves HTTP. Add a scenario when a change touches a hot path (cached
reads, uploads, index generation, authz resolution) or adds a new kind of traffic.

## Layout

```
perf/
├── k6/config.js               BASE_URL, token and fixture names, all from __ENV with defaults
├── k6/helpers.js              authHeaders, getOk, payload builders
├── k6/scenarios/NN_<name>.js  numbered, one traffic shape each
├── config.perf.toml           server config the perf run starts with (fixed tokens, perf-* names)
└── results/                   summary JSON per run; baselines committed per release
```

## Writing a scenario

Template: `templates/perf/k6/scenarios/01_warm_read.js`.

- The doc comment at the top says what the scenario measures, which setup task it needs
  (`task perf:seed`) and how to run it.
- `options.stages` ramps up, holds and cools down. Note the req/s each stage roughly reaches, so a
  reader can relate the numbers to their own hardware.
- **Thresholds:**
  - `http_req_failed: ["rate<0.01"]` is a hard requirement in every scenario.
  - Latency (`p(95)`, `p(99)`) is a target. `perf:run:<name>` enforces it; `perf:run:all` passes
    `--no-thresholds` and reports only, so one slow scenario doesn't hide the others' results.
- `check()` asserts both the status and the body (non-empty, the right content type). A fast 200
  with an empty body is a failure.
- Generate payloads natively (`crypto.getRandomValues` + `k6/encoding`). Building bytes in a JS loop
  starves the k6 runner and ends up measuring k6 instead of the server.
- Upstreams are mocked with a local mock server. Never load-test someone else's registry.

## Comparing runs

Each `perf:run:*` writes `perf/results/<scenario>.json` (`--summary-export`).
`task perf:report:compare BASE=perf/results/v1.2.3` compares p95 per scenario against a baseline
directory and reports regressions beyond `MARGIN` percent (default 25); `FAIL=1` makes it exit
non-zero. Commit the baseline from each release run.

## Optional heavier runs (add when needed, no template)

Batlehub runs each of these from its own workflow, triggered by a PR label of the same name (the
label is removed after the run) or by manual dispatch:

- **soak**: hours at moderate load across every variant (one "arm" per registry kind). The gate is
  memory growth (RSS slope), not latency. A gate test keeps the arms in sync with the enum.
- **breaking-point**: ramp until `http_req_failed` crosses a threshold; record the VU count.
- **profile**: run a scenario under `perf record` and render a flamegraph (inferno). Weekly cron.
- **db-call budget**: count SQL statements per request against a committed JSON budget.

Metrics while running: `perf/scripts/run_with_metrics.sh` samples the server's RSS and CPU next to
k6. Copy it from batlehub when resource numbers matter, not only latency.
